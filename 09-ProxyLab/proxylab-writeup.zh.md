## 1. 引言（Introduction）

**Web 代理（proxy）**是一个在浏览器和最终服务器之间扮演"中间人"角色的程序。浏览器不直接联系最终服务器获取网页，而是先联系代理，由代理把请求转发给最终服务器；当最终服务器回复代理时，代理再把回复转发给浏览器。

代理有很多用途：
- 有时被用在**防火墙**里：防火墙后面的浏览器只能通过代理访问防火墙外面的服务器；
- 可以充当**匿名化工具**：通过去掉请求中的所有身份信息，代理可以让浏览器对 Web 服务器保持匿名；
- 还可以用来**缓存 Web 对象**：在本地保存服务器对象的一份副本，之后遇到同样的请求时直接从缓存读出回复，而不必再次与远程服务器通信。

在这个实验里，你要编写一个**缓存 Web 对象的简单 HTTP 代理**。实验分三部分：

- **第一部分**：让代理能接受入站连接，读取并解析请求，把请求转发给 Web 服务器，读取服务器的响应，再把响应转发给对应的客户端。这部分会让你学习 HTTP 的基本运作方式，以及如何用 socket 编写跨网络连接的通信程序。
- **第二部分**：升级代理，同时处理多个并发连接。这会让你接触并发——一个至关重要的系统概念。
- **第三部分**：用一块简单的**内存缓存**，保存最近访问过的 Web 内容，给代理加上缓存。

## 4. 第一部分：实现一个顺序代理（Implementing a sequential web proxy）

第一步是实现一个基本的**顺序代理**，处理 HTTP/1.0 的 GET 请求。其他请求类型（如 POST）是严格可选的。

代理启动后，应在**命令行指定**的端口上监听入站连接。一旦连接建立，代理应读取客户端的**完整请求**并解析它：判断客户端是否发送了合法的 HTTP 请求；如果是，代理再建立到对应 Web 服务器的连接，并请求客户端指定的对象。最后，代理读取服务器的响应并转发给客户端。

### 4.1 HTTP/1.0 GET 请求

当用户在浏览器地址栏输入类似 `http://www.cmu.edu/hub/index.html` 的 URL 时，浏览器会向代理发送一个 HTTP 请求，请求行可能类似：

```
GET http://www.cmu.edu/hub/index.html HTTP/1.1
```

此时，代理至少要解析出以下字段：
- **主机名（hostname）**：`www.cmu.edu`；
- **路径或查询串及其后的一切**：`/hub/index.html`。

这样代理才能确定：它应该连接到 `www.cmu.edu`，并发送一条自己的 HTTP 请求，请求行形如：

```
GET /hub/index.html HTTP/1.0
```

注意：HTTP 请求中每一行都以回车符 `\r` 加换行符 `\n` 结尾。同样重要的是，**每个 HTTP 请求都以一个空行 `"\r\n"` 结束**。

注意上面例子中：浏览器的请求行以 `HTTP/1.1` 结尾，而代理发出的请求行以 `HTTP/1.0` 结尾。现代浏览器会生成 HTTP/1.1 请求，但你的代理应该处理它们，并**作为 HTTP/1.0 请求转发**。

还要认识到：HTTP 请求，哪怕是 HTTP/1.0 GET 请求这一子集，也可能极其复杂。教科书描述了 HTTP 事务的某些细节，但 HTTP/1.0 的**完整规范请参考 RFC 1945**。理想情况下，你的 HTTP 请求解析器应该完全健壮，符合 RFC 1945 的相关章节——只有一处例外：规范允许**多行请求字段**，但不要求你的代理正确处理它们。当然，你的代理**绝不能因为畸形请求就提前终止**。

### 4.2 请求头（Request headers）

本实验重要的请求头是 `Host`、`User-Agent`、`Connection` 和 `Proxy-Connection`：

- **总是发送 `Host` 头。** 虽然在技术上这不符合 HTTP/1.0 规范，但它是让某些 Web 服务器（尤其是使用虚拟主机技术的服务器）给出合理响应的必要手段。
  `Host` 头描述最终服务器的主机名。例如，要访问 `http://www.cmu.edu/hub/index.html`，你的代理应发送如下头：
  ```
  Host: www.cmu.edu
  ```
  浏览器有可能在自己的请求里自带 `Host` 头。如果是这样，你的代理应该沿用浏览器发的同一个 `Host` 头。

- **你可以选择总是发送如下 `User-Agent` 头：**
  ```
  User-Agent: Mozilla/5.0 (X11; Linux x86_64; rv:10.0.3) Gecko/20120305 Firefox/10.0.3
  ```
  （原文因排版把它分在两行，你的代理应作为**单行**发送。）
  `User-Agent` 头标识客户端（操作系统、浏览器等参数），Web 服务器经常利用这些信息调整它们提供的内容。发送这个特定的 `User-Agent` 字符串，可能让你在简单 telnet 式测试时，获得的内容在内容和多样性上都更好。
  **为了方便，上面这个 `User-Agent` 头的值已经在 `proxy.c` 中作为字符串常量提供给你。**

- **总是发送如下 `Connection` 头：**
  ```
  Connection: close
  ```

- **总是发送如下 `Proxy-Connection` 头：**
  ```
  Proxy-Connection: close
  ```

  `Connection` 和 `Proxy-Connection` 头用来指明：在第一次请求/响应交换完成后，连接是否保持打开。让你的代理**为每个请求都新开一条连接**是完全可行（也是被建议）的做法。把这两个头的值指定为 `close`，就是告诉 Web 服务器：你的代理打算在第一次请求/响应交换后关闭连接。

最后，如果浏览器在 HTTP 请求里附带任何额外的请求头，你的代理应该**原样转发**它们。

### 4.3 端口号（Port numbers）

本实验有两类重要的端口：**HTTP 请求端口**和**你的代理的监听端口**。

- **HTTP 请求端口**是 HTTP 请求 URL 中一个**可选**字段。也就是说，URL 可能是 `http://www.cmu.edu:8080/hub/index.html` 这种形式，此时你的代理应连接到主机 `www.cmu.edu` 的 **8080** 端口，而不是默认的 HTTP 端口 80。无论 URL 中是否包含端口号，你的代理都必须正常工作。
- **监听端口**是你的代理监听入站连接的端口。你的代理应接受一个**命令行参数**指定监听端口号。例如，下面的命令让代理在端口 15213 上监听：
  ```bash
  linux> ./proxy 15213
  ```
  你可以选择任何**非特权**监听端口（大于 1024、小于 65536），只要它没被其他进程占用。因为每个代理必须使用唯一的监听端口，而且同一台机器上常常有很多人同时工作，所以提供了 `port-for-user.pl` 脚本帮你挑选属于自己的端口号。用你的用户 ID 生成端口：
  ```bash
  linux> ./port-for-user.pl droh
  droh: 45806
  ```
  `port-for-user.pl` 返回的端口 p 永远是**偶数**。所以如果你还需要一个端口（比如给 Tiny 服务器用），可以放心使用端口 p 和 **p+1**。
  **请不要自己随便挑一个随机端口**。如果这样做了，你就有可能与别的用户互相干扰。

## 5. 第二部分：处理多个并发请求（Dealing with multiple concurrent requests）

一旦顺序代理能工作了，你就应该改造它，让它**同时**处理多个请求。实现并发服务器最简单的方式，是**为每个新连接请求派生一个新线程**。其他设计也完全可以，例如教科书 12.5.5 节描述的**预线程化（prethreaded）服务器**。

- 注意：你的线程应该运行在**分离（detached）模式**下，以避免内存泄漏。
- 教科书（CS:APP3e）里描述的 `open_clientfd` 和 `open_listenfd` 函数，基于现代、与协议无关的 `getaddrinfo` 函数，因此是**线程安全**的。

## 6. 第三部分：缓存 Web 对象（Caching web objects）

实验的最后一部分，是给代理加一个缓存，把最近使用的 Web 对象保存在内存里。HTTP 其实定义了一套相当复杂的模型：Web 服务器可以指示它们提供的内容应如何被缓存，客户端也可以指定缓存应如何代表它们使用。不过，你的代理采用一个**简化方案**。

当你的代理从服务器收到一个 Web 对象时，在把它传送给客户端的同时，应在内存里缓存它。如果另一个客户端向同一个服务器请求同一个对象，你的代理**不必重新连接服务器**，直接重发缓存的对象即可。

显然，如果代理把每个被请求过的对象都缓存下来，就需要无限的内存。而且，因为有些 Web 对象比别的大，一个巨大的对象可能占满整个缓存，让其他对象完全没机会被缓存。为避免这些问题，你的代理应同时有**最大缓存大小**和**最大缓存对象大小**两个上限。

### 6.1 最大缓存大小（Maximum cache size）

整个缓存的大小上限如下：

```
MAX_CACHE_SIZE = 1 MiB
```

计算缓存大小时，你的代理**只能统计用于存放实际 Web 对象的字节**；任何额外字节，包括元数据，都应忽略。

### 6.2 最大对象大小（Maximum object size）

你的代理**只缓存**不超过下面上限的 Web 对象：

```
MAX_OBJECT_SIZE = 100 KiB
```

为了方便，两个大小上限都作为**宏**在 `proxy.c` 中提供。

实现正确缓存的最简单方式：为每个活动连接分配一个缓冲区，随服务器数据的到达不断累加。如果缓冲区大小超过最大对象大小，就丢弃该缓冲区。如果在超过最大对象大小之前已读完全部响应，就可以缓存这个对象。用这种方案，你的代理为 Web 对象使用的数据总量最多是（T 为最大活动连接数）：

```
MAX_CACHE_SIZE + T * MAX_OBJECT_SIZE
```

### 6.3 淘汰策略（Eviction policy）

代理的缓存应采用一种**近似 LRU（最近最少使用）**的淘汰策略。不一定要严格 LRU，但要合理地接近。注意：**读**一个对象和**写**一个对象都算作"使用"该对象。

### 6.4 同步（Synchronization）

对缓存的访问必须**线程安全**，确保缓存访问没有竞态条件，很可能是这一部分实验里更有意思的地方。事实上有一个特殊要求：**多个线程必须能够同时读缓存**。当然，同一时刻只允许一个线程写缓存，但这个限制**不能**加在读者身上。

因此，用一把大的**排他锁**保护整个缓存**不是**可接受的方案。你可以考虑：把缓存分区、使用 Pthreads **读写锁**，或用**信号量**自己实现读写锁方案。不管怎样，"你不必实现严格 LRU"这一点，会给你支持多读者带来一些灵活性。

### 7.2 健壮性（Robustness）

## 8. 测试与调试（Testing and debugging）

除了简单的自动评分器，你不会得到任何样例输入或测试程序来测试你的实现。你必须自己设计测试，甚至自己搭一套**测试工具**，来帮助你调试代码、判断实现什么时候才算正确。这在现实世界是宝贵技能——真实世界的运行条件很少是已知的，参考解常常不存在。

好在有很多工具可以用来调试和测试代理。务必**覆盖所有代码路径**，并测试一批有代表性的输入，包括基本情况、典型情况和边界情况。

### 8.1 Tiny Web 服务器

handout 目录里有 CS:APP 的 **Tiny Web 服务器**源码。虽然不如 thttpd 强大，但 CS:APP 的 Tiny Web 服务器很容易按你的想法修改。它也是你代理代码一个合理的起点。而且它就是 driver 代码用来取页面的服务器。

### 8.2 telnet

如教科书（11.5.3 节）所述，你可以用 telnet 打开到代理的连接，并发送 HTTP 请求。

### 8.3 curl

你可以用 curl 向任何服务器（包括你自己的代理）生成 HTTP 请求。它是极其有用的调试工具。例如，如果代理和 Tiny 都跑在本机，Tiny 监听在端口 15213，代理监听在端口 15214，那么可以用下面的 curl 命令，**经你的代理**请求 Tiny 上的一个页面：

```bash
linux> curl -v --proxy http://localhost:15214 http://localhost:15213/home.html
```

curl 会输出详细过程：先连接代理（`127.0.0.1` 端口 15214），再发送 `GET http://localhost:15213/home.html HTTP/1.1`（带 `User-Agent`、`Host`、`Accept`、`Proxy-Connection` 头），随后收到 Tiny 的 `HTTP/1.0 200 OK` 响应（含 `Server`、`Content-length`、`Content-type` 头）和 HTML 正文。观察这些输出，你可以直接验证代理有没有正确转发请求和响应。

### 8.4 netcat

netcat（又叫 nc）是一个多用途网络工具。你可以像用 telnet 一样用 netcat 打开到服务器的连接。例如，假设你的代理跑在 catshark（CMU 校内机器）的端口 12345 上，可以这样手动测试代理：

```
sh> nc catshark.ics.cs.cmu.edu 12345
GET http://www.cmu.edu/hub/index.html HTTP/1.0

HTTP/1.1 200 OK
...
```

除了连接 Web 服务器，netcat 本身也可以当服务器。用下面的命令，netcat 就在端口 12345 上监听：

```
sh> nc -l 12345
```

一旦搭好 netcat 服务器，你就可以通过代理请求它上面的一个**假对象**，然后检查你的代理发给 netcat 的**确切请求**长什么样。

### 8.5 Web 浏览器

> [CMU 校内测试方式。本机是纯 CLI 环境、没有图形浏览器，请用 8.3 的 curl 或 8.4 的 netcat 代替。]

最终你应该用最新版的 Mozilla Firefox 测试代理。访问"关于 Firefox"会自动把浏览器更新到最新版。配置 Firefox 使用代理：`偏好设置 > 高级 > 网络 > 设置`。

看到一个真实 Web 浏览器跑在你的代理上会非常兴奋。虽然代理功能有限，你会注意到它能浏览绝大多数网站。

一个重要的告诫：**用浏览器测试缓存时必须非常小心**。所有现代浏览器都有自己的缓存，在测试代理的缓存之前，你应该先**禁用浏览器自身的缓存**。

## 10. 提示（Hints）

- 如教科书 10.11 节所述，对 socket 输入输出使用**标准 I/O 函数**是有问题的。相反，我们建议你使用 **RIO（健壮 I/O）包**，它在 handout 目录的 `csapp.c` 文件里提供。
- `csapp.c` 里提供的**错误处理函数**不适合你的代理：因为服务器一旦开始接受连接，就不应该终止。你需要修改它们，或自己写。
- 你可以**任意修改** handout 目录里的文件。例如，为了良好的模块化，你可以把缓存函数实现成 `cache.c` 和 `cache.h` 两个库文件。当然，添加新文件需要你更新提供的 Makefile。
- 如教科书 CS:APP3e 第 964 页旁注所讨论的，你的代理必须**忽略 SIGPIPE 信号**，并优雅地处理返回 **EPIPE** 错误的写操作。
- 有时，对一个**被提前关闭**的 socket 调用 `read` 接收字节，会导致 `read` 返回 -1 且 `errno` 被设为 **ECONNRESET**。你的代理也不应因为这个错误而终止。
- 记住，网上并不是所有内容都是 ASCII 文本。网络上有大量内容是**二进制数据**，比如图片和视频。选择和使用网络 I/O 函数时，务必考虑到二进制数据。
- 即使原始请求是 HTTP/1.1，也一律把请求**作为 HTTP/1.0 转发**。
