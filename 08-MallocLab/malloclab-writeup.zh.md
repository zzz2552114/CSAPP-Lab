## 4. 如何做这个实验（How to Work on the Lab）

你的动态存储分配器由以下**四个函数**组成，它们在 `mm.h` 中声明、在 `mm.c` 中定义：

```c
int mm_init(void);
void *mm_malloc(size_t size);
void mm_free(void *ptr);
void *mm_realloc(void *ptr, size_t size);
```

我们给你的 `mm.c` 文件实现了一个我们能想到的、最简单但仍功能正确的 malloc 包。以它为起点，修改这些函数（也可以定义其他私有的静态函数），使它们遵守以下语义：

- **`mm_init`**：在调用 `mm_malloc`、`mm_realloc` 或 `mm_free` 之前，应用程序（也就是你用来评估实现的、由 trace 驱动的驱动程序）会调用 `mm_init` 来执行任何必要的初始化，比如分配初始堆区域。如果初始化过程中出现问题，返回值应为 **-1**，否则为 **0**。

- **`mm_malloc`**：`mm_malloc` 例程返回一个指针，指向一个**至少 `size` 字节的已分配块的有效载荷（payload）**。整个已分配块应位于堆区域内，并且不应与任何其他已分配块重叠。

  我们会把你的实现与标准 C 库（libc）提供的 malloc 版本比较。由于 libc 的 malloc 总是返回按 8 字节对齐的有效载荷指针，你的 malloc 实现也应该如此，**总是返回 8 字节对齐的指针**。

- **`mm_free`**：`mm_free` 例程释放由 `ptr` 指向的块，不返回任何值。这个例程只在传入的指针（`ptr`）是由更早的 `mm_malloc` 或 `mm_realloc` 调用返回、且尚未被释放时，才保证正常工作。

- **`mm_realloc`**：`mm_realloc` 例程返回一个指针，指向一个**至少 `size` 字节的已分配区域**，并满足以下约束：
  - 如果 `ptr` 为 NULL，则该调用等价于 `mm_malloc(size)`；
  - 如果 `size` 等于 0，则该调用等价于 `mm_free(ptr)`；
  - 如果 `ptr` 不为 NULL，它必须是由更早的 `mm_malloc` 或 `mm_realloc` 调用返回的。

  `mm_realloc` 调用把 `ptr` 指向的内存块（旧块）的大小改为 `size` 字节，并返回新块的地址。注意新块的地址可能和旧块相同，也可能不同，这取决于你的实现、旧块中的内部碎片量以及 realloc 请求的大小。

  新块的内容与旧 `ptr` 块的内容相同，直到新旧大小的**较小值**为止；其余部分未初始化。例如，如果旧块是 8 字节、新块是 12 字节，那么新块的前 8 字节与旧块的前 8 字节完全相同，最后 4 字节未初始化。类似地，如果旧块是 8 字节、新块是 4 字节，那么新块的内容与旧块的前 4 字节完全相同。

这些语义与相应的 libc `malloc`、`realloc` 和 `free` 例程的语义一致。在 shell 中输入 `man malloc` 可以查看完整文档。

## 5. 堆一致性检查器（Heap Consistency Checker）

动态内存分配器是出了名地难以正确且高效地编程。它们难以正确编写，是因为涉及大量**无类型（untyped）指针操作**。你会发现，编写一个**扫描堆并检查其一致性**的堆检查器会非常有帮助。

堆检查器可以检查的一些例子：

- 空闲链表中的每个块是否都被标记为空闲？
- 是否存在某些相邻的空闲块逃过了合并（coalescing）？
- 每个空闲块是否真的都在空闲链表中？
- 空闲链表中的指针是否指向有效的空闲块？
- 是否有已分配块相互重叠？
- 堆块中的指针是否指向有效的堆地址？

你的堆检查器由 `mm.c` 中的函数 **`int mm_check(void)`** 组成。它会检查你认为明智的任何不变量或一致性条件。**当且仅当**你的堆一致时，它才返回非零值。你不限于上面列出的建议，也不要求检查全部内容。当 `mm_check` 失败时，鼓励你打印错误消息。

这个一致性检查器是供你在开发过程中自己调试用的。提交 `mm.c` 时，**确保删除对 `mm_check` 的所有调用**，因为它们会拖慢你的吞吐量。你的 `mm_check` 函数会获得**风格分**。一定要加入注释，记录你在检查什么。

## 6. 支持例程（Support Routines）

`memlib.c` 包为你的动态存储分配器模拟内存系统。你可以在 `memlib.c` 中调用以下函数：

- **`void *mem_sbrk(int incr)`**：把堆扩展 `incr` 字节，其中 `incr` 是正的非零整数，并返回一个指向新分配堆区域第一个字节的通用指针。语义与 Unix 的 `sbrk` 函数相同，区别在于 `mem_sbrk` 只接受正的、非零的整数参数。

- **`void *mem_heap_lo(void)`**：返回指向堆中第一个字节的通用指针。

- **`void *mem_heap_hi(void)`**：返回指向堆中最后一个字节的通用指针。

- **`size_t mem_heapsize(void)`**：返回堆当前的字节大小。

- **`size_t mem_pagesize(void)`**：返回系统的页大小（以字节为单位，Linux 系统上为 4K）。

## 7. 由 Trace 驱动的驱动程序（The Trace-driven Driver Program）

`malloclab-handout.tar` 分发中的驱动程序 `mdriver.c` 会测试你的 `mm.c` 包的**正确性、空间利用率和吞吐量**。驱动程序由一组包含在分发中的 trace 文件控制。每个 trace 文件包含一系列分配、重新分配和释放指令，指示驱动程序按某种顺序调用你的 `mm_malloc`、`mm_realloc` 和 `mm_free` 例程。这个驱动程序和这些 trace 文件，就是我们评分你的 handin `mm.c` 文件时使用的同一套。

`mdriver.c` 驱动程序接受以下命令行参数：

- `-t <tracedir>`：从目录 `tracedir` 中查找默认 trace 文件，而不是使用 `config.h` 中定义的默认目录。
- `-f <tracefile>`：只使用某一个特定的 trace 文件进行测试，而不是使用默认的一组 trace 文件。
- `-h`：打印命令行参数的摘要。
- `-l`：除了学生的 malloc 包之外，还运行并测量 libc 的 malloc。
- `-v`：详细输出。以紧凑表格形式打印每个 trace 文件的性能明细。
- `-V`：更详细的输出。处理每个 trace 文件时打印额外的诊断信息。调试时很有用，可以确定是哪个 trace 文件导致你的 malloc 包出错。

## 8. 编程规则（Programming Rules）

- 你不应该改变 `mm.c` 中任何接口。
- 你不应该调用任何与内存管理相关的库调用或系统调用。这排除了在代码中使用 `malloc`、`calloc`、`free`、`realloc`、`sbrk`、`brk` 或这些调用的任何变体。
- 你不允许在 `mm.c` 程序中定义任何**全局或静态的复合数据结构**，比如数组、结构体、树或链表。但是，你可以在 `mm.c` 中声明全局标量变量，比如整数、浮点数和指针。
- 为了与 libc malloc 包一致（它返回按 8 字节边界对齐的块），你的分配器**必须总是返回按 8 字节边界对齐的指针**。驱动程序会为你强制这个要求。

## 9. 评分（Evaluation）

如果你违反了任何规则，或者你的代码有 bug 导致驱动崩溃，你将得 **0 分**。否则，你的分数按以下方式计算：

- **正确性（20 分）**：如果你的解决方案通过了驱动程序执行的正确性测试，你将获得满分。每个正确的 trace 都会给你相应的部分分数。

- **性能（35 分）**：用两个性能指标来评估你的解决方案：
  - **空间利用率（Space utilization）**：驱动程序实际使用的内存总量（即通过 `mm_malloc` 或 `mm_realloc` 分配但尚未通过 `mm_free` 释放的内存）与你的分配器使用的堆大小之间的**峰值比率**。最优比率等于 1。你应该找到好的策略来最小化碎片（fragmentation），使这个比率尽可能接近最优。
  - **吞吐量（Throughput）**：每秒完成操作的平均次数。

  驱动程序通过计算一个**性能指标（performance index）P** 来汇总你的分配器的性能，P 是空间利用率和吞吐量的加权和：

  ```
  P = wU + (1 - w) · min(1, T/Tlibc)
  ```

  其中 U 是你的空间利用率，T 是你的吞吐量，Tlibc 是你的系统在默认 trace 上 libc malloc 的估计吞吐量（注 1）。这个性能指标**更看重空间利用率而不是吞吐量**，默认权重 w = 0.6。

  考虑到内存和 CPU 周期都是昂贵的系统资源，我们采用这个公式来鼓励你在内存利用率和吞吐量之间进行**均衡的优化**。理想情况下，性能指标将达到 P = w + (1 - w) = 1，也就是 100%。由于每个指标对性能指标最多贡献 w 和 1-w，你不应该极端地只优化内存利用率或只优化吞吐量。要获得好成绩，你必须**在利用率和吞吐量之间取得平衡**。

- **风格（10 分）**：
  - 你的代码应该分解为函数，并尽可能少用全局变量。
  - 你的代码应该以一个头部注释开头，描述你的空闲块和已分配块的结构、空闲链表的组织方式，以及你的分配器如何操作空闲链表。
  - 每个子程序都应该有一个头部注释，描述它做什么以及如何做。
  - 你的堆一致性检查器 `mm_check` 应该**全面且有良好的文档**。

  你会因一个良好的堆一致性检查器获得 5 分，因良好的程序结构和注释获得 5 分。

> 注 1：Tlibc 的值是驱动中的一个常量（600 Kops/s），由你的授课老师在配置程序时确定。

## 11. 提示（Hints）

- **使用 `mdriver -f` 选项**。在初始开发阶段，使用微型 trace 文件会简化调试和测试。我们提供了两个这样的 trace 文件（`short1,2-bal.rep`），可以用于初始调试。

- **使用 `mdriver -v` 和 `-V` 选项**。`-v` 选项会给出每个 trace 文件的详细摘要。`-V` 还会指示每个 trace 文件何时被读取，这有助于你隔离错误。

- **用 `gcc -g` 编译并使用调试器**。调试器能帮你隔离和识别越界（out of bounds）的内存引用。

- **理解教材中 malloc 实现的每一行**。教材里有一个基于隐式空闲链表（implicit free list）的简单分配器的详细示例。把它作为出发点。在你完全理解简单隐式链表分配器的一切之前，不要开始动手写你自己的分配器。

- **把指针算术封装在 C 预处理宏中**。内存管理器中的指针算术因为需要大量强制类型转换而令人困惑、容易出错。通过为你的指针操作编写宏，可以显著降低复杂度。参见教材中的示例。

- **分阶段实现**。前 9 个 trace 只包含 malloc 和 free 请求。最后 2 个 trace 包含 realloc、malloc 和 free 请求。我们建议你先让你的 malloc 和 free 例程在前 9 个 trace 上正确且高效地工作，然后再把注意力转向 realloc 实现。起步时，可以先把 realloc 建立在现有 malloc 和 free 实现之上。但要获得真正好的性能，你需要构建一个独立的（stand-alone）realloc。

- **使用剖析器（profiler）**。你会发现 `gprof` 工具对优化性能很有帮助。

- **尽早开始！** 用几页代码写一个高效的 malloc 包是可能的。但我们能保证，这将是你到目前为止职业生涯中写过的最困难、最精巧的一些代码。所以尽早开始，祝你好运！
